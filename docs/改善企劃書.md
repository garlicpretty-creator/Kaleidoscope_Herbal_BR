# 森羅物語：草本 — 重製版 v1.1 改善企劃書

- 基準：`Kaleidoscope_Herbal_v1.2.13.mcaddon`（舊線最終版）
- 本線：重製版，版本自 **1.1.0** 起算
- 狀態：第一版草案，隨實作更新

## 1. 摘要

重製版 1.1.0 已完成四件事：

1. 把 1.2.13 的行為包與資源包原樣納入版本庫，版本號改為 1.1.0，版本只寫在一處。
2. 開放對外 API（握手、清單查詢、寒熱讀寫、外部食物寒熱登記、熱源標籤），並附可直接複製的 SDK。契約見 [API.md](API.md)。
3. 全面檢查 PBR：124 組 texture set 全數合格，另列出 7 項待美術確認的改善。規範與結果見 [PBR.md](PBR.md)。
4. 建立測試、PBR 檢查與打包工具。

玩法、數值、貼圖在 1.1.0 **沒有變動**。接下來的工作排在第 6 節的里程碑。

**需要你決定的一件事（第 2 節）：版本號從 1.2.13 降到 1.1.0，而 UUID 沿用。** 已安裝 1.2.13 的世界不會自動換成 1.1.0。

## 2. 版本重製的影響與決定

| 項目 | 1.1.0 的做法 | 原因 |
|---|---|---|
| 版本號 | 兩個 manifest、模組、相依、圖鑑、Tavern 註冊一律 1.1.0 | 依指示重製為 1.1 |
| UUID | 沿用 1.2.13 的 UUID | 砂鍋、百子櫃、曬籃、香爐的存檔與玩家寒熱值都綁在行為包上；換 UUID 等於換一個包，這些資料會讀不到 |
| 版本來源 | `scripts/data/version.js` 一處，測試核對 manifest 與圖鑑是否一致 | 1.2.13 的版本字串散落在 4 個檔案 |

風險：遊戲以 UUID 加版本辨識資源包，1.1.0 比 1.2.13「舊」。已套用 1.2.13 的世界會繼續用 1.2.13，
玩家必須手動在世界設定裡改選 1.1.0。尚未在實機驗證匯入行為，發布前要測。

| 方案 | 做法 | 代價 |
|---|---|---|
| A（目前） | 沿用 UUID，版本 1.1.0 | 舊世界需手動切換；發布說明要寫清楚 |
| B | 沿用 UUID，版本改 1.3.0，對外名稱仍叫「重製版 1.1」 | 舊世界自動升級；版本號與名稱不一致 |
| C | 換新 UUID，版本 1.1.0 | 視為全新模組；舊世界的工作站內容與寒熱值不會帶過來 |

建議：若有玩家的世界正在用 1.2.x，選 B；若重製版只給新世界用，維持 A。

程式內的 `v1.2.x` 註解是舊線的修改紀錄，保留作為歷史；重製版的新註解標 `v1.1.0`。

## 3. 現況盤點

| 類別 | 內容 |
|---|---|
| 檔案 | 940 個（行為包 + 資源包），打包後約 680 KB |
| 藥材 | 11 種：人參、當歸、甘草、靈芝、金銀花、枸杞、紅棗、艾草、菊花、茯苓、冬蟲夏草（後兩者不可栽培） |
| 方塊 | 60 個：藥草與作物 20、工作站 3（砂鍋、藥缽、香爐）、擺設與可擺放藥膳 37 |
| 物品 | 94 個 |
| 配方 | 合成 20 個；湯劑方 3 個（人參、四物、靈芝），各有下／中／上三品 |
| 世界生成 | feature 32、feature rule 21、結構 2（森林與針葉林藥廬） |
| 腳本 | 52 檔約 2,300 行，另有圖鑑資料 199 KB；`@minecraft/server` 2.7.0，最低引擎 1.26.1 |
| 語言 | zh_TW、zh_CN、en_US，各 551 行 |
| PBR | 124 組 texture set |
| 既有聯動 | Cookery（配方、圖鑑）、Tavern（藥酒）、A Witch Way（自動餵食、天象、催化）、魔女手札（森羅週曆） |

1.2.13 之前草本只當「客戶端」：向 Cookery、Tavern 註冊自己的內容，並單向廣播 `evt`。
別的模組沒有辦法問草本任何事，也無法讓自己的內容參與寒熱系統。這是 1.1.0 API 要補的缺口。

## 4. 改善項目

優先度：P0 = 發布 1.1.0 前、P1 = 1.1.x、P2 = 之後。

### 4.1 對外 API 與模組握手

| # | 項目 | 優先度 | 狀態 |
|---|---|---|---|
| A1 | `api_ping` / `api_ready` 握手，回報版本、capabilities、限制 | P0 | 完成 |
| A2 | `catalog`：查詢藥材與藥膳（含寒熱值、藥效） | P0 | 完成 |
| A3 | `constitution` / `constitution_write`：讀取與調整玩家寒熱 | P0 | 完成 |
| A4 | `external_heat`：其他模組替自己的食物登記寒熱值 | P0 | 完成 |
| A5 | 方塊標籤 `kaleidoscope_herbal:heat_sources` 作為砂鍋熱源 | P0 | 完成 |
| A6 | 新事件 `constitution`（上火／受寒） | P0 | 完成 |
| A7 | 複製即用的 SDK `sdk/herbal-client.js` | P0 | 完成 |
| A8 | 實機測試：與 Cookery、Tavern、AWW 同時載入時的握手順序 | P0 | 未做 |
| A9 | `external_decoctions`：外部模組註冊湯劑方與佐使藥材 | P1 | 規劃 |
| A10 | `external_processing`：外部模組註冊曬籃、鍘刀、藥碾、藥缽配方 | P1 | 規劃 |
| A11 | 更多事件：曬製完成、切製、研磨、採收野生藥草 | P1 | 規劃 |
| A12 | 圖鑑擴充：外部模組在草本圖鑑加頁 | P2 | 規劃 |

設計原則（已落實於 A1–A7）：

- 只收腳本送出的事件，玩家的 `/scriptevent` 無法改寒熱值。
- 所有輸入都驗證；登記有筆數上限（256）；寒熱調整有幅度（±50）與頻率（每秒一次）限制。
- 不能覆寫草本或原版物品的數值；同一物品先登記者保有。
- 草本不保存外部登記，對方每次收到 `api_ready` 重送，世界存檔不會因此變大。
- 沒裝草本時 SDK 完全安靜，對方模組照常運作。

A9、A10 之所以排在 P1：湯劑的三品成品各是獨立物品與方塊，工作站的展示用方塊狀態索引（上限 16 值）也寫死了物品清單。
要先把這兩處改成資料驅動（見 B3），外部配方才有地方顯示。

### 4.4 內容與體驗

以下是盤點時看到的缺口，是否要做由你決定。

| # | 觀察 | 可能方向 | 優先度 |
|---|---|---|---|
| C1 | 湯劑方只有 3 個，11 種藥材中艾草、菊花、金銀花、茯苓、冬蟲夏草沒有主方 | 增加方劑，或把佐使系統擴大 | P1 |
| C2 | 沒裝 Cookery 時只提示一次「配方停用」，切片、製茶等流程會中斷 | 明確定義獨立模式下哪些流程可用，並在圖鑑隱藏不可用的頁 | P1 |
| C3 | 寒熱系統刻意不顯示文字，只有粒子與音效 | 保留設計，但在圖鑑加一頁說明徵兆 | P2 |
| C4 | 茯苓、冬蟲夏草不可栽培 | 維持稀有，或提供後期栽培手段 | P2 |
| C5 | en_US 與 zh_CN 行數齊全但未經校閱 | 校稿 | P2 |

### 4.5 效能與穩定

舊線 1.2.6 已做過一輪最佳化（閒置時不跑計時器、存檔節流、大批次分幀）。重製版維持這些做法，另需注意：

| # | 項目 | 優先度 |
|---|---|---|
| S1 | 每個工作站一筆世界動態屬性，大量擺放時的容量與載入時間需量測 | P1 |
| S2 | 新 API 每個請求最多回覆數封訊息，需在多模組同時握手時量測尖峰 | P0（併入 A8） |
| S3 | 催化掃描約 2,100 格，已分幀；多個催化同時發生時需量測 | P2 |
